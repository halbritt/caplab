Locator format is `SRC-X: chapters/<file>.md :: <exact Markdown heading>`. All final IDs are lowercase, source-independent, and use a stable namespace plus a kebab-case name. Kinds are limited to `principle`, `heuristic`, `transformation`, `pattern`, `anti-pattern`, `proof-obligation`, `tradeoff`, `smell`, `constraint`, and `terminology`.

Provenance relations mean:

- `direct_support`: the source explicitly states the operational claim.
- `corroboration`: the source independently supports substantially the same claim.
- `refinement`: the source narrows applicability, adds an evidence gate, or supplies language/context mechanics.
- `derived_inference`: the formulation is a bounded synthesis from cited source material, not a direct author claim.
- `tension`: the formulation is a competing position that must remain visible rather than being merged into consensus.

### Deliberately distinct concepts

| Concepts kept distinct | Why merging would erase an operational decision |
|---|---|
| `universal.evidence-before-intervention` vs `universal.authority-discipline` | Evidence can support a diagnosis or recommendation without granting execution or acceptance authority. |
| `universal.behavior-preservation` vs `testing.contract-derived-protection` | Preservation is the obligation; tests/characterization are one proof mechanism and must not define unauthorized behavior. |
| `universal.local-reasoning` vs `implementation.reader-oriented-obviousness` | Local reasoning is a structural goal; obviousness is the reader-tested presentation property used to assess it. |
| `complexity.change-amplification`, `complexity.cognitive-load`, and `complexity.unknown-unknowns` | APOSD defines three different symptoms with different evidence and interventions; averaging them into “complexity” would weaken diagnosis. |
| `design.information-hiding` vs `design.information-leakage` | One is a design principle; the other is a diagnostic smell. Leakage can exist despite private declarations. |
| `design.deep-module` vs `design.earned-abstraction` | Depth measures interface leverage after a boundary exists; earned abstraction decides whether a boundary should exist at all. |
| `design.knowledge-duplication` vs `design.information-leakage` | Duplication is one leakage mechanism; ordering, representation, and policy can leak without duplicated syntax or rules. |
| `design.coherent-routine-extraction` vs `design.arbitrary-size-threshold` | Extraction is a transformation earned by a seam; size threshold is an anti-pattern that cannot supply that evidence. |
| `design.law-of-demeter` vs `design.direct-dependency-when-indirection-hides-nothing` | These are competing heuristics selected by ownership hiding and interface cost; neither supersedes the other. |
| `design.metadata-driven-configuration` vs `design.configuration-interface-cost` | One externalizes real policy; the other accounts for the public cognitive/operational cost and guards overuse. |
| `implementation.error-semantics` vs `implementation.error-surface-reduction` | Error meaning is the contract; reducing handler sites is an optional design pattern constrained by that contract. |

| `testing.test-first-feedback` vs `testing.abstraction-before-feature-test-sequence` | Both are valid and sometimes competing orderings; repair strongly favors failing-test-first while shared API design may require abstraction work first. |

| `python.mutable-ownership` vs `universal.structured-lifecycle` | Python alias/call-by-sharing mechanics need a targeted lens while the universal lifecycle applies to all resources and tasks. |
