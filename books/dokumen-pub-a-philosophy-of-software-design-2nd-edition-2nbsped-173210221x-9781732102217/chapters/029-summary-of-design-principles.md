# Summary of Design Principles

Summary of Design Principles

Here are the most important software design principles discussed in this book:

1.  Complexity is incremental: you have to sweat the small stuff (see [p. 11](007-2-the-nature-of-complexity.md#part0006.xhtml#a27C)).

2.  Working code isn’t enough (see [p. 14](008-3-working-code-isnt-enough.md#part0007.xhtml#a27G)).

3.  Make continual small investments to improve system design (see [p. 15](008-3-working-code-isnt-enough.md#part0007.xhtml#a27H)).

4.  Modules should be deep (see [p. 23](009-4-modules-should-be-deep.md#part0008.xhtml#a27S))

5.  Interfaces should be designed to make the most common usage as simple as possible (see [p. 27](009-4-modules-should-be-deep.md#part0008.xhtml)).

6.  It’s more important for a module to have a simple interface than a simple implementation (see [pp. 61](013-8-pull-complexity-downwards.md#part0012.xhtml), [74](014-9-better-together-or-better-apart.md#part0013.xhtml#a2C7)).

7.  General-purpose modules are deeper (see [p. 39](011-6-general-purpose-modules-are-deeper.md#part0010.xhtml)).

8.  Separate general-purpose and special-purpose code (see [pp. 45](011-6-general-purpose-modules-are-deeper.md#part0010.xhtml#a28E), [68](014-9-better-together-or-better-apart.md#part0013.xhtml#a292)).

9.  Different layers should have different abstractions (see [p. 51](012-7-different-layer-different-abstraction.md#part0011.xhtml)).

10. Pull complexity downward (see [p. 61](013-8-pull-complexity-downwards.md#part0012.xhtml)).

11. Define errors out of existence (see [p. 81](015-10-define-errors-out-of-existence.md#part0014.xhtml#a29B)).

12. Design it twice (see [p. 91](016-11-design-it-twice.md#part0015.xhtml)).

13. Comments should describe things that are not obvious from the code (see [p. 101](018-13-comments-should-describe-things-that-arent-obvious-from-the-code.md#part0017.xhtml)).

14. Software should be designed for ease of reading, not ease of writing (see [p. 151](023-18-code-should-be-obvious.md#part0022.xhtml)).

15. The increments of software development should be abstractions, not features (see [p. 156](024-19-software-trends.md#part0023.xhtml)).

16. Separate what matters from what doesn’t matter and emphasize the things that matter (see [p. 171](026-21-decide-what-matters.md#part0025.xhtml)).
