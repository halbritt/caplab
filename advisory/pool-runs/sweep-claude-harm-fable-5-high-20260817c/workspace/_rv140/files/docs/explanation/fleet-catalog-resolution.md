# Fleet Catalog Resolution

Purpose: explain why a fleet repository's drive resolves a *merged* catalog after the product/instance division, and why this is a loader delivery rather than a new architectural rule.

## The gap the division opened

`product-instance-divided@1` (Discovery 0019 — the instance is not the product) moved every foreign-subject target-state predicate out of the product catalog and into the instance repository. That is exactly right for the compiler's own graph: striatum-next drives against the generic lifecycle and standing-capability predicates, all of which stay in the product catalog beside the structural vocabulary (passes, gates, artifact-kinds, IRs, pipelines). The compiler's own drive never named a foreign target-state, so the division never had to say how a foreign target-state would be found.

A *fleet* repository does name them. Praxis's `reminder-bot-product`, `frontier-verified`, and their kin describe praxis compilations; under Discovery 0019 they are instance evidence and live in the instance catalog (`striatum-instance/striatum-next/catalog/target-states/`). But the compiler that drives praxis loads its vocabulary from a single root, and after the division no single root is whole:

- The **product** root carries the structural vocabulary and the generic states, but not praxis's foreign target-state — a request for it is an unknown target.
- The **instance** root carries the foreign target-state, but no `passes/` — a load of it errors on the missing subdirectory.

Neither root alone resolves. The division split the vocabulary along an ownership cut that is correct for durability but that no loader knew how to re-join at drive time.

## Why it is delivery, not a decision

The catalog model (RFC 0001/0005) fixes what the vocabulary *means* — a target-state is a versioned predicate over the artifact graph; a pass is a versioned transformation contract — but it never fixed the vocabulary's on-disk *arity*. A catalog assembled from a base directory plus overlay directories is the same catalog, with the same semantics, as one assembled from a single directory. Overlaying changes how the loader reads the vocabulary off disk; it changes nothing about the vocabulary. So this closes the gap by delivery under P2/N11 — no RFC clause is amended, no new durable concept is introduced.

The composition is not arbitrary. D0011.C1 makes the core graph another graph's pinned environment: the shipped compiler product *is* the fleet repository's environment. So the product catalog is the natural **base**, and the fleet's own foreign target-states — its instance's contribution — are the **overlay** layered on top. The direction of layering falls straight out of the ownership relation the division already established.

## The shape

`LoadCatalog(root, overlays...)` reads the base root exactly as before — the full structural and generic vocabulary — then, for each overlay root in order, layers its `target-states/` on top. Three properties make the merge safe and honest:

- **Overlays contribute target-states only.** An overlay carries no passes, gates, or kinds; the structural vocabulary has exactly one home, the base. This keeps the ownership cut sharp — an instance never redefines a pass — and it is why an overlay's absent `target-states/` subdirectory is tolerated rather than an error: an overlay may legitimately carry none.
- **Later overlay wins, deterministically.** On a target-state id collision the last overlay in flag order wins, in the order given. Precedence is explicit and reproducible; catalog maps stay stably iterated.
- **No overlays is byte-identical to today.** A drive that names no overlay loads exactly the base catalog the shipped compiler loads standalone. The non-fleet path does not change — the guard test pins this alongside the resolution property.

At the CLI, `-catalog-overlay` is a repeatable flag layered over `-catalog`. Because a fleet drive dispatches lanes and wakes itself after commit from a detached supervisor with an unrelated working directory, `wakeCommand` re-emits each overlay as an absolute path — the post-commit wake resolves the same merged catalog the session did, or the foreign state in flight would vanish under the wake.

## What it is worth

The mechanical substance is a standing guard: a base catalog overlaid with a foreign target-state resolves that state while the base-only load never gains it, later-overlay-wins holds, and a structurally-partial overlay is tolerated. That guard plus the pass-bracket floor is the honest evaluation bound of `fleet-catalog-resolution@1`. This is a loader-shape delivery; it does not route itself through the Dual-Signal funnel, so it closes at the floor — `Asserted`, honestly. Earning `Verified` for a change like this is what `evolution-earns-verified` names, through the compiler's own funnel; it is not smuggled in here.

The division made the catalog durable by cutting it in two. This makes it *usable* by a fleet repository again, by teaching the loader to re-join the halves at drive time along the same ownership seam the division cut.

## Registration-derived resolution (`fleet-catalog-resolution@2`)

The v1 seam left one thing hand-passed: someone had to know where the instance lives and say `-catalog-overlay` on every invocation. `@2` moves that knowledge to where it already belonged — the repository's registration. A registered repository's workstation-registry entry may declare, under `resolution.instance_catalog_overlay`, the single overlay root of its instance catalog. This is repository policy the driver reads, never compiler semantics: nothing about what a catalog *means* changed, only where the driver learns which overlay to compose. A registry written before the declaration existed decodes unchanged — the key is optional and absent by default.

Resolution happens once per invocation, at the session-construction seam — after the graph opens (so the repository is named by its registered identity) and before the catalog loads. The rules, in force order:

- **Explicit flags override.** Any `-catalog-overlay` on the invocation is the effective list, exactly as given, in flag order; registration is not consulted. Override, never append — an operator who names overlays gets precisely those.
- **Registration derives.** With no flag, a declared `instance_catalog_overlay` becomes the single-element effective list: a plain `striatum -repo <fleet> drive` resolves the merged catalog with nothing hand-passed.
- **Absence is silence.** A repository declaring nothing loads the base catalog exactly as before — the non-fleet drive is byte-identical to the pre-declaration one.
- **A used declaration must be usable.** The declared root must be an absolute, clean path naming an existing readable directory; a violation — like a registry that cannot be read at the resolution point — refuses the invocation *before* any catalog load, as a registration-resolution failure naming the repository and the offending path. The failure is configuration, surfaced near its cause, never a degraded catalog. A valid root without `target-states/` remains v1's tolerated empty overlay; the composition semantics above are untouched.
- **The wake receives a snapshot.** The effective list is re-emitted to the post-commit wake and the standing liveness timer as explicit absolute `-catalog-overlay` argv, so a wake resolves the same merged catalog its session did — through the flags-override branch, by construction. A wake never re-reads registration; a declaration edited mid-flight changes the next fresh session, not a wake already armed.

Every verb that opens graph and catalog resolves the same way — `drive`, `status`, `accept`, and kin all see one merged catalog for a registered fleet repository; this is session construction, not a drive special case. The authoring surface stays deliberately thin: no CLI verb writes the declaration yet, so the v1 authoring path is a direct edit of the workstation `registry.json` — a `striatum` setter verb is a new surface decision, not smuggled in here.

## Companion: a fleet repository's checks resolve to the repository too (`checks-resolve-to-repo@1`)

Catalog resolution is one half of a single property — *a fleet repository is compiled and verified on its own terms.* Resolving the catalog said **what target states a fleet repository can name**; it says nothing about **what teeth bite its change-sets.** That is the check registry, and it had the same latent defect one layer down.

The check registry is per-repo policy (RFC 0010): a content-addressed set of checks resident in the repository's own tree at `policy/checks/repository.json`, describing that repository's verification. But the `-checks` flag resolved its relative path against the *process working directory*, not `-repo`. On the compiler's self-drive the two coincide — the working directory *is* the target repository — so the defect was invisible. It surfaces the moment the compiler drives a foreign repository from its own directory: it looks for the registry under its own tree, finds its own registry or none, and verifies the fleet repository's change-sets on the compiler's terms. A fleet drive could resolve praxis's target states while still gating them on striatum-next's Go checks — exactly the language-hardwiring `praxis-earns-verified` fought, resurfacing at the path-resolution layer.

The fix is symmetric with catalog resolution and just as small: a relative `-checks` resolves against `-repo`, so the registry a drive loads is the one in the target repository's tree. An absolute `-checks` is an explicit override, honored as given. The self-drive, where `-repo` defaults to the working directory, resolves to the same file it always did — byte-identical. And because a fleet drive wakes itself after commit from a detached supervisor with an unrelated working directory, the resolution runs once at session build and the wake re-emits the already-repo-relative path (absolutized), so the wake never re-resolves the registry against the supervisor's directory.

Like catalog resolution, this is delivery, not a decision: the check model already fixes the registry as per-repo policy resident in the repository's tree; resolving its path relative to the repository it belongs to is fixing *where the loader looks*, not changing *what a check means* (P2/N11, no clause amended). The two halves converge on a single shape — registration. The catalog half arrived at `fleet-catalog-resolution@2` above: the registration's `resolution` object now derives the overlay. The check half arrived at `checks-resolve-to-repo@2`: the same `resolution` object carries a `check_registry` sibling, and a registered fleet repository's check registry auto-resolves from it — a plain `striatum -repo <fleet> drive` gates on the fleet repo's own checks with no hand-passed `-checks`. Both halves now share one precedence rule (an explicit flag overrides and registration is never consulted — for `-checks`, explicitness is a parse-time fact, so passing the default string or the empty string is explicit too; declaring nothing is byte-identical silence), one refusal shape (a declared-but-unusable value refuses before anything loads, as a registration-resolution failure naming the repository and the offending path — for checks, the declared path must be an absolute, clean path to an existing readable regular file), and one wake-pinning discipline (the effective decision is re-emitted verbatim to every wake surface — for checks, including the *empty* decision, pinned as an explicit empty `-checks` and rendered in the timer unit as systemd's literal `""` — so a wake never re-reads registration).

Two structural differences distinguish the check half, both deliberate. First, the field is pointer-shaped: absent and present-empty are distinct states — a registry that never declares saves byte-identically to the pre-declaration shape, while a declared-empty `check_registry` is a declaration, refused at the point of use like every other unusable declared value. Second, refusal reach on `accept`/`reject`: checks resolution sits in `buildSession` (the session-construction seam), not in the graph-and-catalog opening the recording path calls, so a broken `check_registry` declaration never blocks recording a verdict — the bounded transition is silently skipped under its standing best-effort contract, no session (and so no weakened drive) ever comes into being, and the loud refusal arrives on the next session-constructing invocation. A broken *overlay* declaration, by contrast, refuses `accept`/`reject` before the ledger mutation, because the catalog is a genuine input of recording. The asymmetry follows the seam placement; strengthening the loudness is a registered deferral (`docs/reference/deferrals.md`).
