    "rfcs/0008-scheduler-and-capacity-policy/design.md": "# RFC 0008 Design: Scheduler and Capacity Policy\n\n## Status\n\nAccepted (Epoch 2 Runtime Foundation Pass, 2026-07-02). Vocabulary: RFC 0001, plus the Language Amendments section below. Directory formerly `0008-scheduler-and-quota-policy`; quota is a capacity kind, not a core term (D0001.C7) — the word survives only in policy documents.\n\nThis RFC defines placement policy and capacity accounting. It redefines no artifact meaning, no gate, no claim. The Scheduler is a deterministic pure function that binds lanes to execution backends under versioned policy, treats capacity — vendor quota, local compute, Principal attention — as accounted, estimated, expiring resources, and converts capacity that would otherwise expire into durable evidence.\n\n## The Scheduling Function\n\n### Signature\n\n```text\nschedule(\n    ready_set:            [PlannedPassRun],       # from Driver plan records (RFC 0006)\n    lane_requirements:    [LaneRequirement],      # from pass contracts + pipeline wiring (RFC 0004)\n    backend_declarations: [BackendDeclaration],   # from backends/ (RFC 0007)\n    capacity_snapshot:    CapacitySnapshot,       # content-addressed workstation derived-store view\n    telemetry_snapshot:   TelemetrySnapshot,      # content-addressed derived-store view (empty at v1)\n    policy:               PolicyPins,             # {scheduler, quota, repository} content hashes\n    as_of:                Instant                 # injected; the scheduler owns no clock\n) → SchedulingDecision                            # bindings + deferrals + refusals + budgets + next_horizon\n```\n\nThe Scheduler is a library the Driver invokes, not a process. It owns no wall-clock, no store, no state between invocations. Every time-dependent quantity (reset horizons, reserve ramps, deferral retries) is computed from `as_of` and snapshot data. All inputs are sealed: the ready set is read from plan records, the snapshots are content-addressed derived-store views, the policy is pinned by content hash.\n\n### Inputs\n\n**PlannedPassRun** — the scheduler-facing slice of the Driver's plan record (seam with RFC 0006; fields this RFC requires):\n\n| Field | Meaning |\n|---|---|\n| `pass_run_id` | identity of the planned run |\n| `pass_id`, `contract_version` | catalog reference |\n| `posture`, `posture_version` | for `review` runs (demand and harvest) |\n| `mode` | `demand` \\| `harvest`, assigned at planning (see Objective) |\n| `subject_pins` | input artifact pins (churn detection, independence ancestry, dedupe) |\n| `lane_requirement_refs` | the lanes this run needs placed |\n| `priority_basis` | critical-path depth toward the requested target predicate; compilation-request deadline if any |\n| `attempt`, `excluded_backends` | re-dispatch lineage carried from the closed predecessor run (see Failure Interpretation) |\n| `residual_of` | set when this run covers the missing lanes of a partial submission (residual run; owner RFC 0010) |\n\n**LaneRequirement** (declared by pass contracts, RFC 0004; carried per planned run):\n`{requirement_id, role, write_scope, independence: required | preferred | none, independence_subject_pins, context_class, capability_needs, synthesis_position}`.\n\n**BackendDeclaration** (seam with RFC 0007, which owns the schema; fields consumed here):\n`{backend_id, aliasing_class, supported_pass_types, forbidden_pass_types, capability_facts, context_limit, latency_profile, concurrency_slots, quality_profile, capacity_pools_served, capacity_signal_support, runtime_profiles}`.\nDeclarations describe; policy prefers. The scheduler reads declarations as facts and policy as preference — never the reverse.\n\n**CapacitySnapshot / TelemetrySnapshot** — content-addressed views of the two named derived stores below, folded under the Derived-State Doctrine (D0002.C2): rebuilt from ledgers by `reconcile`, pinned by hash so every binding names the exact folded state it was computed from.\n\n### Output: the SchedulingDecision\n\nOne invocation produces exactly one `scheduling_decision` record (the audit unit) plus zero or more `lane_binding` records. Full schemas below. The decision contains:\n\n- **bindings** — lane bindings minted this evaluation.\n- **deferrals** — ready runs not bound now, each with a closed reason code and a `retry_at` horizon.\n- **refusals** — ready runs unbindable under any current input, each with a closed reason code. Refusals return to the Driver; **the Driver escalates, never the scheduler** — escalation is the Driver's only interruptive act (D0002.C5).\n- **harvest_budget** — per-pool expiring-capacity budget published for the Driver's harvest planner.\n- **next_horizon** — the earliest instant at which re-evaluation could change any outcome (nearest reset, reserve-ramp threshold, deferral retry, dispatch horizon). The Driver persists this value into a durable timer unit rewritten each drive session; a standing timer is the documented liveness floor. Wake mechanics are RFC 0006's; the horizon is data.\n\n**Record-then-dispatch ordering is binding:** `pass_run_opened` → `scheduling_decision`/`lane_binding` → bundle materialization → adapter dispatch. Records always precede work. All appends go through the Graph Store's append API under its append lock (RFC 0009).\n\n### Determinism\n\nThe scheduler is deterministic: identical input tuples produce identical SchedulingDecisions, bit for bit. Tiebreaking is a total lexicographic order — `(mode, priority class, critical-path depth desc, subject identity, backend preference rank, backend_id)` — with no randomness; where load-spreading needs variation, the variation derives from a hash of the sealed inputs. Consequences:\n\n1. **Replay and audit.** Any binding is re-derivable: fetch the pinned snapshots and policy hashes, re-run the function, get the same bindings and trace. \"Why did this review run on that backend\" is a computation, not archaeology — the placement-plane analogue of D0004.C6's provenance replay.\n2. **Shadow evaluation.** A proposed policy change is evaluated by re-running historical pinned input tuples under the candidate policy and diffing the bindings — what makes v4 self-tuning honest.\n3. **The Driver stays a program.** A stochastic scheduler would smuggle nondeterminism into the deterministic Driver loop (D0002.C5).\n4. **Disputes are decidable.** Whether capacity pressure influenced a placement is answered by re-running and inspecting the trace.\n\nThe determinism is conditional on the capacity snapshot, and that is honest: capacity state is estimated and time-varying, so \"was this the right binding\" factors into \"was the snapshot accurate\" (an estimation question) and \"was the function correct given the snapshot\" (a replayable question). Conflating the two is how schedulers become unexplainable.\n\n### Invocation cadence\n\nEvent-driven, no polling. The Driver invokes the scheduler when: (1) a plan record adds runs to the ready set; (2) a submission arrives or a lapse is observed; (3) a `capacity_observation` record lands; (4) any pinned policy file's content hash changes; (5) `reconcile` completes; (6) the previously published `next_horizon` arrives. The scheduler never sleeps, ticks, or watches; it is called with the world as data.\n\n## The Capacity Model\n\n### Capacity Pools\n\nCapacity is accounted in **Capacity Pools**: named, bounded, possibly-resetting accounts declared in `policy/quota.yaml`. Every pool has:\n\n```text\npool_id · kind · window {none | rolling(duration) | calendar(period, anchor)}\nsize {estimate, floor, ceiling, confidence, learn: bool, prior}\nremaining (derived) · reset_at (derived or learned) · reserve schedule\n```\n\nFour capacity kinds, closed per policy schema version:\n\n1. **`vendor_quota`** — subscription capacity behind a vendor harness. Frequently multi-window: one backend may serve several pools simultaneously (a rolling session window and a calendar weekly window); a binding debits all pools its backend serves. Sizes are usually unknown and must be learned.\n2. **`local_compute`** — workstation resources (GPU slots, CPU-heavy verifier lanes). Non-depleting, non-resetting; shaped as **slots** (concurrency), not volume. Never expires, so never harvested — but it contends, so it is scheduled.\n3. **`principal_attention`** — Principal attention is a capacity pool, and it is the scarcest resource in the 2031 scale directive. `size` is a **declared policy estimate** (acceptance items plus escalation resolutions the Principal can absorb per day); a lint forbids telemetry-derived values for this field. `remaining` is derived from open acceptance gates and unresolved escalations, summed globally across all registered graphs. The scheduler never schedules the Principal and never blocks a gate (an open acceptance gate is explicit state, D0005.C4); the pool exists to **pace producing work**: binding-time throttling of runs whose completion terminates in Principal-facing output, and harvest suppression. Capacity pressure at the production end of the pipe, never at the gate. **The split with RFC 0006:** this RFC owns the pool and its accounting; RFC 0006 owns the deferral behavior (deferring dispatch of acceptance-terminal steps). Both read the same workstation derived store; neither ever weakens a gate. The v1 shape is stated out loud: acceptance throughput bounds compiled-intent throughput — the Principal is the pipeline's rate limit; the relief valve is an Epoch 3 graduated-acceptance/delegation RFC, not a scheduler knob.\n4. **Wall-clock is not a pool.** Deadlines and latency are constraints on individual runs (from compilation requests and pass advisory resources), not an account anyone debits. Time appears only in windows, horizons, and deadline constraints.\n\n### Capacity state is a workstation-level derived store\n\nCapacity is global to the workstation, not to one graph: vendor pools and the Principal are shared by every registered graph. The **capacity-state** derived store therefore lives at `$XDG_DATA_HOME/striatum/derived/`, owned by this RFC, stored and governed per RFC 0009's derived-store rules (own transactional cursor per store; rebuildable; never migrated). It folds, in ledger order over **all registered graphs**:\n\n- `capacity_observation` records — usage debits, refusal signals, reset detections;\n- `lane_binding` records — estimated debits at dispatch, reconciled against observed usage on submission;\n- `dispatch_lapse` records — burns with no result (the debit stands; silence still spent capacity);\n- pool declarations from the pinned `quota.yaml`.\n\nDrive sessions snapshot it at open; Principal attention is summed globally across graphs. Each materialized view is content-addressed: the `capacity_snapshot_hash` pinned by every binding names the exact folded state. Destroying the store is never data loss; `reconcile` rebuilds it from the ledgers (D0002.C2).\n\n### Estimation without vendor APIs\n\nNo vendor reliably exposes remaining quota; the design assumes zero cooperative vendor APIs and treats any that exist as bonus evidence. Three estimation sources, in increasing strength:\n\n1. **Burn-rate observation.** Every submission carries whatever usage hints the adapter can extract (tokens, requests, wall time — RFC 0007 seam). The fold aggregates debits per pool since the last reset marker. Where hints are absent, the fold uses per-`(pass, posture, context_class)` cost priors from `quota.yaml`, refined by telemetry at v3.\n2. **Refusal classification.** Adapters classify backend failures into a closed `capacity_signal` vocabulary: `exhausted | throttled | degraded | none` (RFC 0007 declares which signals each adapter can distinguish, via `capacity_signal_support`). An `exhausted` signal is the strongest observation in the system: it pins `remaining := 0` for the implicated pools regardless of the running estimate (`refusal_floor: true`). Backends self-reporting refusals is the ground truth that keeps estimates honest.\n3. **Reset inference.** Where windows are undocumented, the fold learns them: an `exhausted` pool that later accepts work implies a reset between the observations; repeated cycles bound the period. Priors live in `quota.yaml`; learned values carry confidence and decay (`confidence_decay`) so a stale estimate degrades toward its conservative floor rather than being trusted forever.\n\n**Conservatism policy:** each pool carries `(floor, estimate, ceiling)`. Demand scheduling spends against `estimate`; harvest budgets are computed from `floor` early in a window and relax toward `estimate` as reset approaches — the cost of over-estimating collapses near reset (exhausting one hour early loses one hour; exhausting on day one of a week loses the week).\n\n## The Objective\n\n### Statement\n\n> Maximize expected engineering value delivered through gates, subject to: hard placement constraints (capability, forbidden pass types, context limits, effect-class restrictions, disjoint write scopes), independence requirements, latency/deadline constraints, repository policy, and capacity accounting — while arriving near zero remaining expiring capacity shortly before each reset.\n\nThe objective is realized as a **lexicographic rule order**, not a scalarized utility function. A weighted utility would be tunable but unexplainable; a rule order makes every binding's WHY a finite trace of rule matches. The order:\n\n1. **Hard constraints filter.** A backend is a candidate for a lane iff: the pass type is supported and not forbidden; declared context limit ≥ the run's context class; effect class permitted; the aliasing-class exclusion set is satisfied for `independence: required`; repository policy does not forbid it; a concurrency slot exists; write-scope disjointness holds against in-flight bindings.\n2. **Demand before harvest.** A `demand` run always outranks a `harvest` run for the same slot or capacity. Harvest never occupies capacity that queued demand work can use before its deadline or the window close.\n3. **Within demand: critical path, then quality matching.** Runs are ordered by critical-path depth toward the requested target predicate, then by level (higher-ambiguity passes first — a blocked design blocks everything under it). Placement prefers the highest `quality_profile` capable backend for judgment-heavy passes (`design-convergence`, gating `review`) and throughput-profile backends for bounded work (`verification` re-runs, mechanical scans) — expressed as ordered `placement_rules` in policy, never hard-coded.\n4. **Within harvest: the harvest rank, within published budgets.**\n\n### The mode split is structural, not modal\n\nThere is no global \"quality-first mode\" versus \"harvest mode\" switch. **Mode is a property of the planned pass run** (`mode: demand | harvest`), assigned at planning time by the Driver: runs required by an active compilation request's target predicate are demand; runs instantiated from the harvest backlog are harvest. Placement rules match on mode. Quality-first behavior for demand work is structural — no state transition can degrade it, because there is no state.\n\n### The D0002.C9 boundary, made mechanical\n\n\"Capacity pressure never touches check gates, review gates, or claim minting\" is enforced by input signatures and record schemas, not exhortation:\n\n- **Gate evaluation takes no capacity inputs.** The Driver's gate evaluator (RFC 0006) has the signature `evaluate(gate_predicate, artifact_version, evidence) → gate_result`; there is no parameter through which capacity state can arrive. Schema lint refuses any gate definition in `catalog/gates/` referencing capacity, pools, or policy files.\n- **Claim computation reads evidence bindings only** (D0005.C5). This RFC's record types carry no claim fields, no verdict fields, no gate fields; a scheduler that wanted to mint a claim has no vocabulary to say it in.\n- **Pass contracts declare resources as advisory only** (D0004.C5 `resources:`); lint refuses capacity terms in `consumes`, `invariants`, or `gates` sections.\n- **Harvest changes what runs, never what passes.** Harvest instantiates cataloged posture parameterizations (D0004.C4); it cannot weaken a required posture, skip a required review, or substitute a cheaper gate — those are pipeline/gate wiring, owned by catalogs, invisible to policy.\n- **Rescheduling invalidates nothing** (D0004.C2); binding, deferring, re-dispatching, and killing harvest lanes move no heads and decay no claims.\n\nThe zero-at-reset objective therefore influences exactly two things: when ready runs get bound (ordering and deferral) and which harvest runs the Driver is asked to plan (the published budget). Nothing else in the system can hear capacity speak.\n\n### Arriving near zero: expiry pressure\n\nFor each expiring pool, per evaluation:\n\n```text\nexpected_demand_burn  = Σ estimated cost of ready + forecast demand runs before reset\nreserve               = reserve_fraction(t) × size.estimate     # policy ramp, → floor near reset\nharvest_budget(pool)  = max(0, remaining.estimate − expected_demand_burn − reserve)\n```\n\n`reserve_fraction(t)` is a policy-declared schedule (e.g. 0.35 at window open, ramping to 0.0 over the final hour). All terms are snapshot arithmetic — deterministic, replayable, visible in the decision record. When `harvest_budget > 0`, capacity is expiring: the budget is published to the Driver's harvest planner. When demand forecasts spike, the budget collapses automatically; no one switches modes.\n\n## Harvest Scheduling\n\n### The planning boundary: budget out, runs in\n\nThe scheduler cannot create pass runs — planning is the Driver's (P4: the scheduler places). The harvest loop is a two-party protocol:\n\n1. The scheduler publishes `harvest_budget` per pool in the `scheduling_decision` record, with `window_close`.\n2. The Driver's harvest planner — Driver mechanics executing this RFC's policy (`quota.yaml → harvest`) — selects candidates from the backlog against current graph state and emits ordinary plan records with `mode: harvest`, sized to the budget.\n3. Those runs return in the next ready set; the scheduler binds them only to expiring capacity within the published budget, at the bottom of the lexicographic order.\n\nThe seam stays clean: the Driver knows the graph (what is stale, decayed, thin); the scheduler knows the capacity. Neither impersonates the other.\n\n### Prioritization among harvest candidates\n\nThe backlog (`quota.yaml → harvest.backlog`) is ordered by durable-value rank, most to least durable:\n\n1. **Decay repair** (`verification`, parameterization `reverify-decayed`): re-verification of claims that decayed from Verified on artifacts still required by standing target predicates. Restores the highest lattice point; pure evidence; zero Principal attention.\n2. **Revalidation service** (`review`, posture `revalidation`): stale-marked artifacts not currently on a demand path. Pre-pays the invalidation cascade — when demand arrives, the re-stamp is already licensed. (Stale artifacts on a demand path are demand work, not harvest.) This is the empirical answer to Epoch 1 open question 2: harvest-funded revalidation generates calibration data — clear-rate versus regenerate-rate — at near-zero marginal cost.\n3. **Coverage thickening** (`second-opinion`, `adversarial`): recently accepted heads whose gate-passing evidence is thin — single posture, no adversarial coverage. Directly services independence supply and the dual-signal `verified` predicate (R4): second signals from a different aliasing class are the canonical harvest sink and future promotion fuel.\n4. **Gap analysis** (`test-gap`, `coherence`, `plan-critique`): findings that seed future demand work.\n5. **Freshness scans** (`doc-freshness`, `dependency-audit`, `stale-scan`): broad, low-context, latency-insensitive — ideal for slow or low-quality-profile backends whose capacity would otherwise always expire.\n\n**The no-fake-work rule, made mechanical:** a harvest candidate is admissible iff its output evidence would bind hashes not already bound by unexpired same-posture evidence — dedupe key `(subject content hash, posture, posture_version)`. `harvest.saturation.per_subject_per_window` additionally caps evidence accumulation per subject: a third same-window adversarial review of one design is waste by declaration. Evidence value has diminishing returns; the policy encodes the cliff.\n\n### When harvest must not run\n\nClosed suppression conditions, all mechanical, all evaluated from snapshot data:\n\n1. **Graph churn** (`suppress_when.graph_churn: subject_in_flight`): skip any subject with open candidate versions, in-flight producing runs, or pending upstream re-runs. Evidence minted against hashes about to move is stillborn. At 2031 scale this is the dominant waste mode; the check is cheap (subject pins against the in-flight binding index).\n2. **Principal queue depth** (`suppress_when.principal_queue_gt: N`): when open acceptance gates plus unresolved escalations exceed the threshold, only `attention_cost: none` backlog entries remain eligible (decay repair, revalidation, stale-scan). Findings-producing postures are deferred: flooding a saturated Principal with adversarial findings converts expiring vendor capacity into Principal-attention debt — a strictly bad trade, since Principal attention is the scarcer pool. Every backlog entry declares `attention_cost: none | findings | acceptance`.\n3. **Demand contention:** harvest never takes a backend's last free slot while demand work is queued for it (`reserve_demand_slots`), and a harvest run is bound only if its expected duration fits before `min(window_close, next demand horizon)`.\n4. **Preemption is abandonment, and it is legal:** if demand arrives while harvest lanes hold needed slots, the Driver may kill harvest lanes (crash-only: killing is indistinguishable from a crash). The run closes `pass_run_closed{canceled}` with cause `superseded_by_demand` (closure record owned by RFC 0006); the burned capacity was budgeted to expire anyway; pass purity makes the abandoned work re-dispatchable if the budget reopens. No graceful-preemption protocol exists or is needed.\n\n## Independence Satisfaction\n\n### Binding under anti-aliasing constraints\n\nFor a lane requirement with `independence: required`, the scheduler computes the **exclusion set**: the aliasing classes, backend sessions, and lane attributions appearing in the provenance ancestry of the subject artifact versions — producing execution, synthesis lineage, prior gating reviews — evaluated against the aliasing registry (`backends/aliasing.yaml`, owned by RFC 0007; R5) current at evaluation time, read as data, never for authority. A candidate backend is eligible iff its `aliasing_class` is outside the exclusion set and the backend can provide a fresh session sharing no lineage with the ancestry (a declared RFC 0007 capability). Two backends over one model family share an aliasing class and are never mutually independent (D0005.C5); co-blindness is aliasing. The declaration-freshness conjunct applies at mint time only (reconciliation F4); the placement filter uses the kinship conjuncts.\n\n**Two evaluations, one authority.** The scheduler's independence check is a placement filter; the **authoritative** evaluation happens at claim-minting and review-gate time (RFC 0005 semantics, RFC 0010 runtime), over recorded lane attribution. The redundancy is deliberate: scheduling is not semantic, so a scheduler bug cannot grant independence — the minting gate re-derives it from provenance and refuses. A correct binding makes gate-time success likely; only the gate makes it true. The binding records the exclusion-set hash it satisfied, so scheduler-versus-gate disagreements are diagnosable.\n\n### When independence is unsatisfiable: defer, then escalate; degrade only where independence was never required\n\nModel consolidation makes this the system's long-term supply problem (Epoch 1 open question 5). The resolution is mechanical and split by the requirement's declared strength:\n\n- **`independence: required`** (Verified minting, gating reviews): **never degrade.** A degraded binding would produce evidence the gate must refuse — pure capacity waste plus a false sense of coverage. Instead: defer with reason `independence_unsatisfiable` and a `retry_at` derived from capacity horizons (an independent class's pool may reset; a backend may recover). After the policy-bounded deferral horizon (`deferral.max_defer`), the scheduler refuses, and the Driver escalates with reason `independence_unsatisfiable` — accepted into RFC 0001's closed escalation vocabulary (R2) because the existing codes encode authority and coherence failures while independence exhaustion is a supply failure with distinct resolutions: procure a backend of a new aliasing class, wait, or amend RFC 0005's independence rule (an architecture change, deliberately expensive).\n- **`independence: preferred`** (advisory review, harvest second opinions): **degrade with recorded deviation.** Bind the best available same-class backend; the binding carries `aliasing_deviation: {required_exclusions, violated_by}`; the resulting Review Ledger's attribution shows the overlap, and any gate that counts independent signals simply does not count it. Findings from a co-blind reviewer still have nonzero value; the record keeps anyone from mistaking them for independent confirmation.\n- **Policy can waive nothing that gates check.** Repository policy may relax `preferred` (accept same-class second opinions for a low-stakes repository). It cannot waive `required` — that would let a policy edit alter Verified's meaning (D0002.C9: meaning changes go through catalog/schema plus RFC).\n\nThis interlocks with harvest rank 3: the scheduler's own harvest ranking preferentially spends expiring capacity of underrepresented aliasing classes on coverage thickening, actively cultivating the independence supply it will need.\n\n## Role Qualification and Vendor-Network Admission\n\nThe independence filter above decides *which* eligible backend a run binds to. A distinct, earlier gate decides whether a backend is *eligible at all* for a run's role: the **admission surface** (`internal/scheduler` — `Admit`, `AdmitRun`, `AdmissionDecision`; design C3, C4, C5, C11). It exists because a vendor-hosted agent backend (AGY) is qualified per-role from its own declaration, not from what a run happened to produce.\n\n**Qualification is decided from the declaration, never inferred from a transcript.** Each backend declaration carries a `role_obligation_coverage` table (RFC 0007, declaration_version 7): for every pass role the backend can host, the obligation *classes* the role must cover for its output to be seal-eligible — `required-output`, `change-set`, `analysis-only`, `endpoint-access` — and a `withheld` flag. A backend is admitted for a run's role only when:\n\n1. **the role is declared and not withheld** — a role a backend declares but marks `withheld: true` is refused admission with a typed diagnostic, never run and then rejected; and\n2. **the role's obligations are covered** — every obligation class the run owes (captured from the pass/role declaration at dispatch-build time, never post-run) appears in the declared coverage; and\n3. **the vendor-network reach is authorized** — a backend whose declaration sets `constraints.network: vendor-endpoint-only` (or whose coverage declares `endpoint-access`) reaches an external vendor endpoint, and that endpoint, credential scope, and role must be authorized by `policy/scheduler.yaml → vendor_authorization` (below).\n\nOtherwise the run is **withheld** with an `AdmissionDecision` recorded on the admission surface, carrying one closed **diagnostic class**. The diagnostic class is the retry/reroute key (design C11): the Driver acts on the class, not on prose.\n\n**Closed diagnostic classes** (specific-first precedence: the most fundamental gap is the one reported):\n\n- **`role_withheld`** — the backend declares the role but marks it withheld (or declares no coverage for it). Resolution: requalify the role once the obligation machinery and its acceptance guard are green (design C12). Reroute; it does not clear with time.\n- **`obligation_uncovered`** — the role is not withheld, but the declared coverage omits an obligation class the run owes. Resolution: amend the pass contract's obligations or the backend's declared coverage. Reroute.\n- **`vendor_unauthorized`** — the role is qualified, but the vendor endpoint/credential-scope/role it reaches is not authorized by `vendor_authorization` for this backend and role. Resolution: add a policy grant (an operator decision). Reroute.\n\nEvery qualification/authorization class **reroutes** — the run moves to a different qualified, authorized backend, and if none exists the Driver escalates. None clears with a bare **retry**; each needs a new input (requalification, a pass-contract change, or a policy grant). This is the placement-plane analogue of the independence split: a supply/qualification gap reroutes or escalates, it never spins.\n\n**`vendor_authorization`** authorizes the network reach; it never qualifies a role. Qualification is read from the declaration's `role_obligation_coverage`; this block only grants a `{backend, endpoint, credential_scope, roles}` tuple. The concrete endpoint URL and the credential secret never appear in policy — the endpoint id and scope name are opaque authorization handles; the adapter reads the real values from its sealed environment. `default: withhold` — an unlisted tuple is `vendor_unauthorized`.\n\n**Authorized vendor network use never by itself blocks a seal (design C5).** Once the endpoint/credential-scope/role is authorized, network reach is an ordinary placement fact: `AdmissionDecision.BlocksSeal` is always false, and a qualified, authorized, network-reaching role is admitted. Seal eligibility is decided downstream from obligation coverage (RFC 0009/0010), never from whether the lane touched the vendor endpoint. A withholding is a **pre-dispatch** refusal of admission — it withholds work before it runs; it does not block the seal of already-placed work.\n\n**Two gates, one authority.** This admission surface consults the `role_obligation_coverage` declaration; the binding function (`Bind`) applies `supported_pass_types`, the independence exclusion set, and concurrency. In the requalified end-state (design C12) a proven role appears in both `supported_pass_types` and an un-withheld coverage entry, so the two agree; while a role is withheld, the coverage entry is what yields the typed `role_withheld` diagnostic instead of a bland \"no capable backend\". A declaration carrying no coverage table and no vendor-network posture is admitted exactly as before — surfacing qualification moves no other backend's placement (design C12).\n\n## Policy Schemas\n\nPolicy files are versioned data in git, schema-validated, content-hashed, and **content-addressed into the object store at first pin** — pin resolution never depends on git history (reconciliation F4/F11). Every binding and every scheduling decision pins the content hashes of all three policy files that produced it; policy participates in provenance exactly as decision records do for passes. `reconcile` verifies pinned hashes resolve in the object store.\n\n### `policy/scheduler.yaml`\n\n```yaml\nid: scheduler\nkind: policy\nschema_version: 1          # record-format version; upcast-on-read discipline applies\npolicy_version: 1          # human-meaningful; the content hash is the real pin\ndemand_priority: [critical_path_depth, level_desc, deadline_proximity, subject_age]\ntiebreak: lexicographic    # closed: lexicographic (no alternatives at v1)\n\nplacement_rules:           # ordered; first full match wins; the matched rule id enters the decision trace\n  - id: design-needs-quality\n    match: {pass: design-convergence}\n    prefer: {quality_profile: highest}\n  - id: gating-review-independent\n    match: {pass: review, gating: true}\n    require: {independence: subject}          # restates the contract; rules may restrict, never relax\n  - id: verification-local-first\n    match: {pass: verification}\n    prefer: {backends: [local]}\n  - id: harvest-expiring-first\n    match: {mode: harvest}\n    prefer: {expiring_capacity: true, quality_profile: any}\n\nconcurrency:\n  max_total_lanes: 6\n  reserve_demand_slots: 1                     # harvest never takes the last slot\n\ndeferral:\n  max_defer: {demand: PT4H, harvest: until_window_close}\n\nredispatch:                                   # policy data, not code; see Failure Interpretation\n  dispatch_horizon_multiplier: 3.0            # × expected duration (telemetry or contract advisory)\n  backoff: {base: PT2M, factor: 4, max: PT2H}\n  alternate_after: 1                          # exclude a backend for this work after N lapses on it\n  escalate_after_attempts: 4                  # then refuse retry_exhausted → Driver escalates\n\ntelemetry:\n  influence: none | prefer_only               # v1: none; v3: prefer_only — never unlocks forbidden\n  min_samples: 20\n\nexplainability:\n  record_trace: full                          # every binding carries its rule-match trace\n\nvendor_authorization:                         # §Role Qualification and Vendor-Network Admission\n  default: withhold                           # (endpoint, credential_scope, role) with no grant → vendor_unauthorized\n  grants:\n    - backend: agy\n      endpoint: agy-vendor-endpoint           # opaque endpoint id; the URL lives in the adapter environment\n      credential_scope: agy-vendor-batch      # named scope; the secret never appears in policy\n      roles: [proposal-generation, design-convergence, implementation-planning, packetization, build, review]\n```\n\n### `policy/quota.yaml`\n\nBackend ids in pools reference `backends/` entries; the ids below are placeholders.\n\n```yaml\nid: quota\nkind: policy\nschema_version: 1\npolicy_version: 1\nconstraints:                                   # restated, lint-checked against D0002.C9\n  - Capacity pressure never touches check gates, review gates, or claim minting.\n  - Harvest entries reference cataloged posture parameterizations only; this file defines no passes.\n\npools:\n  - id: vendor-a.session\n    kind: vendor_quota\n    backend: vendor-a\n    window: {kind: rolling, duration: PT5H}\n    size: {estimate: null, floor: conservative_prior, learn: true}\n    reserve: {start_fraction: 0.35, floor_fraction: 0.0, ramp: linear, ramp_window: PT1H}\n  - id: vendor-a.weekly\n    kind: vendor_quota\n    backend: vendor-a\n    window: {kind: calendar, period: P1W, anchor: learned}\n    size: {estimate: null, learn: true}\n    reserve: {start_fraction: 0.25, floor_fraction: 0.0, ramp: linear, ramp_window: PT12H}\n  - id: local.gpu\n    kind: local_compute\n    backend: local\n    window: {kind: none}\n    slots: 1\n  - id: principal.attention\n    kind: principal_attention\n    window: {kind: calendar, period: P1D, anchor: local_midnight}\n    size: {estimate: 12}                       # declared, never telemetry-derived (lint-enforced)\n\nestimation:\n  burn_source: ledger                          # the capacity_observation fold\n  refusal_floor: true                          # adapter-classified `exhausted` pins remaining := 0\n  cost_priors: {default: {per_run: 1.0}}       # refined by telemetry per (pass, posture, context_class)\n  confidence_decay: PT6H\n\nharvest:\n  enabled: true                                # false at v0; activation is a policy commit\n  budget_rule: expiring_minus_reserve          # closed vocabulary of rules\n  suppress_when:\n    principal_queue_gt: 8                      # then only attention_cost: none entries eligible\n    graph_churn: subject_in_flight\n  saturation: {per_subject_per_window: 2, dedupe_by: [subject_hash, posture, posture_version]}\n  backlog:                                     # ordered rank; postures are catalog references (D0004.C4)\n    - {pass: verification, parameterization: reverify-decayed, rank: 1, attention_cost: none}\n    - {pass: review, posture: revalidation,   rank: 2, attention_cost: none}\n    - {pass: review, posture: second-opinion, rank: 3, attention_cost: findings}\n    - {pass: review, posture: adversarial,    rank: 4, attention_cost: findings}\n    - {pass: review, posture: test-gap,       rank: 5, attention_cost: findings}\n    - {pass: review, posture: plan-critique,  rank: 6, attention_cost: findings}\n    - {pass: review, posture: coherence,      rank: 7, attention_cost: findings}\n    - {pass: review, posture: doc-freshness,  rank: 8, attention_cost: findings}\n    - {pass: review, posture: dependency-audit, rank: 9, attention_cost: findings}\n    - {pass: review, posture: stale-scan,     rank: 10, attention_cost: none}\n```\n\n### Repository policy overrides\n\n`policy/repository.yaml` (per target repository) may contribute a `scheduler:` block: additional `placement_rules` (prepended — repository rules match first), `forbidden_backends`, `harvest.enabled`, `suppress_when` thresholds, and pool participation. Merge is deterministic: repository rules **restrict and re-prefer; they cannot relax** — a repository can forbid a backend for sensitive work or disable harvest, but cannot grant an independence waiver, unlock a forbidden pass type, or touch anything gate-adjacent. The merged effective policy is itself content-hashed and pinned by bindings, so which repository's override fired is in the trace.\n\n## Evolution Stages\n\n**v1 — Declarative heuristics.** Ordered `placement_rules`, static harvest ranks, cost priors; `telemetry.influence: none` (the telemetry snapshot hash pins an empty store). Everything above is v1-complete.\n\n**v2 — Repository policy.** Per-repository overlays activate; effective-policy hashing. No change to the function — only richer policy input.\n\n**v3 — Telemetry-informed.** The **scheduler-telemetry** derived store folds ledger outcomes into per-`(backend, pass, posture, context_class)` statistics: attempts, admission rate, gate-refusal rate, `needs_revision` rate, abandonment rate, median latency, observed capacity cost. Influence is bounded by construction: `prefer_only` — telemetry may reorder preferences among already-eligible candidates and refine cost and duration estimates; it can never unlock a forbidden placement, override independence, or promote harvest above demand. `min_samples` guards against noise. v3 also activates quiet-window preference for integration-run placement (reconciliation F5) — a preference; integration semantics remain RFC 0010's. Because the snapshot is content-addressed and pinned, v3 bindings remain exactly as replayable as v1 bindings.\n\n**v4 — Self-tuning = self-hosting.** The scheduler never rewrites its own live policy. Self-tuning is the compiler compiling its own policy: a harvest-funded `review` over scheduler telemetry and shadow-evaluation results produces findings; a policy change enters as an ordinary compiled intent through the IR ladder; shadow evaluation attaches evidence (\"under the candidate policy, the last 500 decisions re-bind as follows\"); the Principal (or a `gates.yaml`-delegated acceptance, never for decision-role artifacts) accepts; the policy commit lands with full provenance. The loop closes without ever becoming hidden.\n\n**Invariants at every stage:**\n\n- **(i) Never semantic.** No stage's output can move a head, mint a claim, alter a gate, or redefine a pass. Enforced by record schemas, not intentions.\n- **(ii) Replayable-from-inputs.** Every binding at every stage is a pure function of pinned, content-addressed inputs. Learned state lives only in derived stores pinned by hash and rebuildable from the ledger — never in opaque runtime memory.\n- **(iii) Explainable.** Every binding carries a `decision_trace`: ordered rule ids matched, constraint filters applied, telemetry factors consulted with values, budget arithmetic. A placement whose explanation is \"the weights said so\" is refused by schema (traces are mandatory fields).\n- **(iv) Policy is versioned data in git.** No stage introduces policy that is not a diffable, hash-pinned commit.\n\n## Failure Interpretation and Re-dispatch\n\n### Silence is the only failure signal\n\nCrash-only backends (D0002.C6) mean the failure model above the seam is: a binding either produces a submission, or nothing. Dead and slow are indistinguishable, and no liveness vocabulary — leases, heartbeats, sessions — may leak into this design; that is Striatum-0's heaviest accidental complexity, deliberately excluded (RFC 0001 retired terms).\n\nEvery binding carries a **dispatch horizon** — `expected_duration × dispatch_horizon_multiplier`, where expected duration comes from telemetry (v3+) or the pass contract's advisory `latency_class` (v1). Horizons are measured in **observed-active time**: intervals containing no drive session and no adapter activity are discounted, so a powered-off workstation does not lapse its own dispatches. When the horizon elapses without a submission, the Driver's deadline sweep appends a `dispatch_lapse` record — an **observation, not an adjudication**: the lane may still be alive. The sweep caps per-session abandonment adjudications with a warning (sweep mechanics are RFC 0006's; the horizon is this RFC's datum).\n\n### Re-dispatch is closure-then-new-run\n\nRe-dispatch is RFC 0010's mechanism, consumed here: the Driver closes the lapsed run (`pass_run_closed{superseded_by_redispatch}`) and opens a new `pass_run_opened` with the same sealed manifest; the incremented `attempt` and inherited `excluded_backends` are carried into the new run's plan slice and `lane_binding`. The scheduler never re-enters a run into the ready set; it sees the successor as ordinary ready work with attempt lineage. (Rejected alternative, load-bearing: same-run attempt+1 re-entry — deleted in reconciliation because it created two live interpretations of one open run.)\n\nAbandonment is provisional (reconciliation F2/F21): a run whose only closure is `abandoned` remains admissible — a late submission is admitted as `submitted_late`; first admitted valid result wins across attempts; a later valid result for a won run appends `redundant_candidate` (value counted, not discarded). Admission is RFCs 0009/0010's; the scheduler's share of the race is double-spent capacity, bounded by the horizon multiplier — a policy knob trading latency against waste, visible in telemetry, tunable at v4. The debits of lapsed bindings stand: silence still spent capacity.\n\n### Re-dispatch policy — policy data, never code, never gates\n\nFrom `scheduler.yaml → redispatch`, informed by provenance history as data:\n\n1. **Backoff:** exponential per (work, backend) — `base × factor^(attempt−1)`, capped. Deterministic from `attempt`.\n2. **Alternate backend:** after `alternate_after` lapses on one backend, that backend joins the successor run's `excluded_backends` (recorded in plan lineage); the next evaluation binds elsewhere if a capable candidate exists.\n3. **Escalation threshold:** after `escalate_after_attempts` total attempts, the scheduler refuses with `retry_exhausted`; the Driver escalates `bounds_exhausted` with `budget_kind: redispatch` (R2; the escalation record's closed `budget_kind` enum names which budget).\n4. **Lapses are capacity evidence:** repeated lapses on one backend inside a window fold into capacity state as a `degraded` observation — vendor outage and silent throttling look identical from here, and both route demand elsewhere. The scheduler notices a down vendor without any liveness machinery.\n5. **Never blocking gates:** all of this is placement-side. A lapse fabricates no gate result, no verdict, no failure artifact. Gates evaluate every admitted candidate; finished lanes' work is never discarded (D0002.C4).\n\n### Residual runs\n\nA `partial` failure mode (D0004 failure semantics) reaches the scheduler as a **residual run** planned by the Driver (`residual_of` set) under RFC 0010's Partial-Admission Closure Rule — RFC 0010 owns the mechanism. This RFC's half is placement: residual lanes inherit attempt lineage per-lane, and their independence exclusion sets include the attributions of the already-submitted sibling lanes — a residual synthesis lane must be independence-coherent with the divergent lanes it will consume (Epoch 1 open question 6, placement half; admission consistency is RFC 0010's half).\n\n## Record Types and Derived Stores\n\nThis RFC owns four ledger record types, registered in `catalog/ledger-record-types/` (one owner per type, R1).
